# 任务三技术说明

## 1. 任务理解

本任务旨在探索利用多模态大模型识别网页截图中的结构化信息，验证大模型在网页内容提取场景下的准确性和局限性。与任务二（CSS Selector / API 提取）不同，任务三采用"截图 + 视觉识别"路线：不直接解析 HTML，而是让模型像人一样"看图识字"，从渲染后的页面截图中提取字段值。

## 2. 整体架构

```
任务二 JSON (100条)
       ↓
数据选择模块 (每页首条已成交)
       ↓
Playwright 截图模块
       ↓
多模态模型 API (Kimi K2.6)
       ↓
结果解析 + Pydantic 校验
       ↓
与任务二参考值比对
       ↓
Excel 导出
```

## 3. 任务二数据如何作为参考值

任务二通过 CSS Selector 解析详情页 HTML 和 API 接口返回数据，提取了每条记录的字段值。任务三使用同一批记录的 `detail_url`，但走完全不同的提取路线：先截图，再用大模型识别截图内容，最后将识别结果与任务二的字段值进行比对。

任务二 JSON 作为"地面真值"（ground truth）的原因是：
- 任务二直接从 HTML 结构中提取，不经过视觉识别环节，准确性高
- 两条路线独立，比对结果能反映视觉识别方案的误差

## 4. 为什么每页选择 1 条已成交记录

从任务二 JSON 前 100 条中，按原有顺序每 10 条为 1 页，从每页选择第一条"已成交"记录，共 10 条。

选择逻辑：
- "已成交"记录包含完整字段（成交时间、竞得人、成交地价等）
- "未成交"记录缺少成交相关字段，不具代表性
- 每页选 1 条保证数据分布均匀，覆盖不同地块类型
- 10 条是实验规模与成本（API 调用费用）的平衡点

## 5. Playwright 如何穿过两层 iframe 并截图

佛山土地交易详情页采用嵌套 iframe 结构：

```
顶层页面
  └── iframe[src*="TDJY_BasicInfoFrame.aspx"]  (第一层)
        └── iframe[src*="TDJY_BasicInfoHistory.aspx"]  (第二层)
              └── 实际内容表格
```

截图流程：
1. Playwright 打开详情页 URL
2. 使用 `page.frame_locator(SELECTOR_OUTER_IFRAME)` 定位第一层 iframe
3. 在第一层 iframe 内继续 `frame_locator(SELECTOR_INNER_IFRAME)` 定位第二层 iframe
4. 在第二层 iframe 内对 `body` 元素调用 `screenshot()`
5. 相邻页面间隔 1 秒，无并发，避免对目标网站造成压力

## 6. 为什么截图阶段不能直接使用 CSS Selector 读取字段

任务三的核心目标是验证"大模型从截图中识别字段"的能力。如果在截图阶段同时用 CSS Selector 读取字段：
- 就失去了任务三的实验意义，变成了任务二的重复
- 模型识别结果无法独立验证，因为已经与 HTML 提取结果耦合
- 截图 + 视觉识别是一条完整的替代路线，应保持独立

因此截图模块仅用 iframe 定位功能进入内容区域，不对任何字段做 CSS Selector 提取。

## 7. 多模态模型选择：Kimi K2.6

选用 **Kimi K2.6** 作为多模态识别模型：
- 支持图片输入（vision 能力）
- 中文理解能力强，适合中文网页截图识别
- 支持 JSON 模式输出，便于结构化解析
- 通过 OpenCode Go 平台调用，使用 OpenAI 兼容接口

模型配置：
- 关闭 thinking（`thinking: {"type": "disabled"}`），避免输出格式不稳定
- 启用 JSON 模式（`response_format: {"type": "json_object"}`），强制返回合法 JSON

## 8. OpenCode Go 的 OpenAI 兼容调用方式

服务商 **OpenCode Go** 提供 OpenAI 兼容的 Chat Completions 接口：

```
POST https://opencode.ai/zen/go/v1/chat/completions
Authorization: Bearer {API_KEY}
Content-Type: application/json
```

请求体格式与 OpenAI 完全一致，包含 `model`、`messages`（含 `image_url` 类型内容）、`max_tokens` 等字段。Kimi K2.6 专用额外参数 `thinking` 和 `response_format` 直接附加在请求体中。

## 9. 图片如何使用 base64 传给模型

截图文件读取为二进制后，通过 Python `base64.b64encode()` 编码为 base64 字符串，拼接为 Data URL：

```
data:image/png;base64,{base64_encoded_image}
```

该 Data URL 作为 `image_url.url` 字段放入消息内容数组中，随文本提示词一起发送给模型。

## 10. 字段识别提示词设计

提示词核心约束：
- 只识别截图中明确可见的文字，不得推断或补全
- 无法确认的字段填写"待核验"，并加入 `uncertain_fields`
- 数值和单位按截图原文填写，不得换算
- `land_usage` 只提取详情页"土地实际用途"，不得使用"土地用途类型"等分类字段
- 只能返回合法 JSON 对象，不得输出 Markdown 代码块或分析过程

提示词包含完整的 JSON 字段模板和字段对应关系，确保模型输出结构固定。

## 11. 关闭 thinking 并启用 JSON 模式

Kimi K2.6 默认会输出 thinking 过程（`<think>...</think>` 标签包裹的推理内容），这会污染 JSON 输出，导致解析失败。因此请求体中加入：

```json
{
  "thinking": {"type": "disabled"},
  "response_format": {"type": "json_object"}
}
```

- `thinking.disabled`：阻止模型输出思考过程
- `json_object`：强制模型返回合法 JSON 对象，降低格式不稳定的风险

## 12. JSON 解析、Pydantic 校验、超时和重试

**解析流程**：
1. 去掉可能的 Markdown 代码块标记（```json / ```）
2. 用正则提取 JSON 对象（`{...}`）
3. `json.loads()` 解析为 Python dict
4. Pydantic `LlmRecognitionResult(**data)` 校验字段类型和必填项

**超时配置**：
- 连接 30 秒，读取 300 秒（大模型响应慢），写入 60 秒，连接池 30 秒

**重试机制**：
- 最大重试 3 次（含首次）
- 触发重试的异常：ReadTimeout、ConnectTimeout、ConnectError、RemoteProtocolError
- 触发重试的 HTTP 状态码：429、500、502、503、504
- 重试间隔：3 秒 × 尝试次数（指数退避）
- 解析失败也会触发重试
- 所有尝试均失败后，记录 parse_error 状态

## 13. raw 响应保存与 `--resume` 断点续跑

每次模型调用成功后，原始响应文本立即保存到 `output/raw_outputs/raw_XX.json`（包装格式：`{"index": N, "raw_response": "..."}`）。

`--resume`（默认启用）模式下：
- 程序检查是否已存在 `raw_XX.json`
- 如果存在且能解析为有效 `LlmRecognitionResult`，则跳过模型调用，直接复用已有结果
- 如果存在但解析失败，则重新调用模型
- 该功能支持实验中断后恢复，也支持分阶段执行（先 `--capture-only` 截图，再完整运行）

## 14. 六个业务字段如何比对

参与比对的业务字段共 6 个：
- `transaction_date`（成交时间）
- `winner`（竞得人）
- `transaction_area`（交易土地面积）
- `transaction_price`（成交地价）
- `land_location`（地块位置）
- `land_usage`（土地用途）

**规范化处理**：
1. 去除首尾空白
2. 去除数字中的逗号分隔符（如 `15,746` → `15746`）
3. 转小写

**匹配规则**：
- 规范化后完全一致 → 匹配
- 数值字段（面积、价格）：提取数字部分，允许 `math.isclose(rel_tol=1e-3, abs_tol=0.01)` 的浮点舍入差异

## 15. 普通识别差异与字段口径差异如何区分

**普通识别差异**：
- 模型无法识别字段（值为空或"待核验"）
- 模型识别值与参考值规范化后确实不一致
- 标记为真正的不匹配，加入 `mismatch_fields`

**字段口径差异（仅针对 `land_usage`）**：
- 模型识别出了有效内容（非空、非"待核验"、未被标注为不确定）
- 识别值与参考值规范化后不一致
- 判断为 API 土地用途分类与详情页土地实际用途的口径差异
- 不加入 `mismatch_fields`，而是加入 `semantic_difference_fields`
- 核验结论标注为"字段口径不同，需人工核验"

区分逻辑：两边都有有效内容但文本不同 → 口径差异；模型无法给出有效内容 → 识别错误/待核验。

## 16. Windows UTF-8/GBK 乱码问题及解决方法

实验过程中遇到过中文乱码问题，原因和解决：

- **原因**：之前对已经是 UTF-8 编码的字符串进行了不必要的二次编码转换（如先 decode 再 encode），导致编码混乱。Windows 默认使用 GBK，但 Python 源码文件本身、JSON 文件和提示词文件都是 UTF-8 编码，问题在于代码中做了错误的编码转换操作。
- **解决**：统一使用 UTF-8，移除所有不必要的编码转换逻辑。所有文件读写操作显式指定 `encoding="utf-8"`；程序输出到终端时设置环境变量 `PYTHONIOENCODING=utf-8`。
- **Excel 本身**：openpyxl 以二进制方式写入 .xlsx，不存在编码问题。

## 17. API Key 安全措施

- API 密钥仅通过 `.env` 文件环境变量传入，不写入源码、README、日志或录屏
- `.env` 已加入 `.gitignore`，不会被提交到版本控制
- `.env.example` 模板文件中只写占位值（`your_opencode_go_api_key_here`）
- 代码中 `get_config()` 函数对外暴露时仅返回模型名称和 API 基础 URL，不暴露密钥内容
- 录屏中命令行输出已确认不包含真实密钥

## 18. 实验结果

本次实验处理 10 条记录，结果如下：

| 指标 | 结果 |
|------|------|
| 处理记录数 | 10 条 |
| 解析成功 | 10 份响应全部解析成功 |
| 成交时间匹配 | 10/10，无普通差异 |
| 竞得人匹配 | 10/10，无普通差异 |
| 交易面积匹配 | 10/10，无普通差异 |
| 成交地价匹配 | 10/10，无普通差异 |
| 地块位置匹配 | 10/10，无普通差异 |
| 土地用途识别 | 10/10，全部被模型识别 |
| 土地用途口径差异 | 10/10，API 分类与详情页实际用途不同 |
| 乱码问题 | 无 |
| 待核验字段 | 0 条 |

**结论**：Kimi K2.6 对中文网页截图的字段识别能力较强，五个普通字段全部正确识别。土地用途的差异来自数据源本身的口径不同（API 返回分类编码 vs 详情页展示实际用途描述），并非模型 OCR 识别错误。

**重要原则**：不能为了显示匹配而把截图识别值替换成 API 分类值。截图识别值必须忠实反映模型从图片中看到的内容。

## 19. 局限性

1. **字段口径差异无法自动解决**：API 分类与详情页实际用途属于不同维度的数据，需要人工理解其对应关系
2. **截图质量依赖目标网站**：如果详情页字体过小、布局混乱或加载失败，会影响识别准确率
3. **模型调用成本**：10 条记录需 10 次 API 调用，大规模采集时成本较高
4. **响应时间**：大模型 API 单次响应需数秒至十几秒，整体流程较慢
5. **iframe 结构耦合**：截图流程依赖特定的 iframe 嵌套结构，目标网站改版后可能需要调整

## 20. 后续改进

1. **字段口径映射表**：建立 API 分类与实际用途的映射字典，将口径差异转化为可自动判断的分类
2. **批量识别优化**：探索单次请求发送多张截图的方式，减少 API 调用次数
3. **截图预处理**：对截图进行裁剪（只保留表格区域）、增强对比度，提升识别准确率
4. **多模型对比**：用多个多模态模型（Claude、Gemini 等）识别同一张截图，对比结果差异
5. **结构化输出增强**：尝试 function calling / tool use 方式替代纯 JSON 模式，进一步提升格式稳定性
